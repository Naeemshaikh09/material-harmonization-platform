**Rules of collaboration**

1. One Git repo; `main` is protected; one branch per feature; pull requests reviewed by developer1 (frontend PRs also by developer2 or 4).
2. **Contracts first:** schemas in `contracts/` are changed only by PR with all four informed. Nobody changes an API shape silently.
3. Every component is built against a mock of its neighbours until the real one lands.
4. Daily 15-minute sync; shared task board; blockers raised the same day.
5. Seed data and migrations are versioned in the repo so any laptop can rebuild the system with one command.
6. Nothing is merged without at least one test (decision logic needs a test per outcome).
7. Freeze code two days before the demo.

## 1. Database

### 1.1 Which database

- **PostgreSQL** (recent version) with: JSONB for variable attributes, `pg_trgm` for fuzzy text search, and optionally `pgvector` for embedding search in the fallback matcher. One database gives uniqueness constraints, transactions (needed for approvals and code supersession) and audit, which a document-only NoSQL store makes harder.
- **There is no ready-made reference database for this PS.** The schema below is **generated by us**. Reference data to seed it is built by developer4: abbreviation and unit dictionaries, grade and rating tables, class templates, and code tables. Public text for training and testing can come from public CPSE tender documents (collected and cleaned by developer4). UNSPSC can optionally inform the class segment; it must be downloaded from its official source and checked for licence terms.
- ORM and migrations: SQLAlchemy + Alembic.

### 1.2 Attribute JSON shape (used in several tables)

Twenty fixed keys: `type, primary_size, length, thickness, material, secondary_material, pressure, temperature, flow, electrical, mechanical_loading, stiffness_hardness, connection, actuation, standard, protection, measurement, coating, manufacturer_part, uom`. Each key holds:

```json
{ "value": "50", "unit": "MM", "code": "0050", "state": "KNOWN",
  "confidence": 0.97, "source_span": "2\"" }
```

`state` is `KNOWN`, `UNKNOWN` (not found) or `NA` (template says not applicable). `NA` is set only from the template, never because extraction failed.

**Audit table protection:** revoke `UPDATE` and `DELETE` on `audit_log` for the application role.

### 1.4 Core logic using the schema

- **Canonical key:** critical dimensions of the class template joined in fixed order, e.g. `0112|0003|DN50|SS316|CL150|FLANGED`. Built only when every critical dimension is `KNOWN` (or template-`NA`).
- **Identity lookup:** `SELECT * FROM cmc WHERE canonical_key=$1 AND status='ACTIVE'`.
- **New CMC:** in one transaction, upsert `cmc_serial` for the coded prefix, increment, compute check digit (Verhoeff), insert `cmc`, insert `crosswalk`, write `audit_log`.
- **Supersession:** one transaction: insert new CMC, set old `status='SUPERSEDED'` and `superseded_by`, re-point active crosswalks, log.

## 3. User flows

**Flow A — Bulk harmonization (Uploader, then system)** Login → CPSE Portal → Upload file → confirm column mapping → processing progress → system runs the pipeline per row (store raw → clean → extract → canonicalize → completeness check → key lookup → fallback match if needed → decide) → counts shown → uploader sees own items with CMC or status.

**Flow B — Search-Before-Create (Uploader)** Type description → system extracts and shows standard description and attributes → outcome: *Existing CMC found* (copy code, link to own code) / *Needs info* (missing fields highlighted, user adds them) / *No match* (request new code) → confirmed new item runs through the same decision → new CMC or pending.

**Flow C — Review (Steward, Approver)** Workbench queue → open task → compare original text, extracted attributes and candidate → choose Approve / Reject / Correct / New → decision applied, crosswalk updated, audit written, task closed. Functional-equivalence and high-value tasks escalate to Approver (L2).

**Flow D — Migration (Admin or Steward)** Choose CPSE and category → dry run → read report → review pending items → publish versioned crosswalk → verify → finalize, or roll back.

**Flow E — Template and dictionary change (Admin)** Edit draft template or code table → diff view → engineer validation noted → activate (new version) → affected records can be re-evaluated; coded-attribute changes trigger supersession.

**Flow F — Audit (Auditor)** Open audit → filter by entity → Verify chain → result valid or first broken entry → anchor hash.

Four attribute states used consistently everywhere: **green = MATCH/KNOWN**, **red = CONFLICT**, **amber = UNKNOWN**, **grey dash = NOT APPLICABLE**. Confidence shown as a small bar. Correct opens an inline editor for attributes; on save the decision reruns. **Golden records tab:** search box and filters, results table, detail page showing standardized description, 20-dimension table (NA as "—", UNKNOWN highlighted amber), CPSE relationship tree, supersession banner, audit timeline, procurement summary.

### developer1 — Tech lead + backend core

**Deliverables**

6. **Canonicalizer:** calls `/extract`, validates against the active template, sets `KNOWN/UNKNOWN/NA`, builds canonical key, completeness.
7. **Decision engine:** outcomes `LINKED / NEW_CMC / PENDING_REVIEW / CONFLICT_NEW`; fast path by key; fallback matcher (class filter, part number equality, trigram text similarity, optional vector search) with per-attribute comparator returning `MATCH/CONFLICT/UNKNOWN`.
8. **CMC service:** serial, Verhoeff check digit, description generator from template, supersession transaction.
9. **API:** all endpoints in Section 2 with OpenAPI; async batch worker.
10. **Migration module:** states and endpoints in 2.6.

### developer2 — AI/ML lead

**Deliverables**

1. **Baseline extractor** (rules + dictionary) behind the `/extract` contract within the first week. This unblocks everyone and becomes the comparison baseline.
2. **Training data pipeline:** convert developer4's labelled train split and synthetic variants into input-text to output-JSON pairs; keep split by item; never touch the test set.
3. **Model fine-tuning:** a small open model with parameter-efficient fine-tuning, or a token-classification encoder; check memory and inference speed early; response target a few seconds per item.
4. **Post-processing:** validate outputs against template and code tables; invalid or low-confidence attributes become `UNKNOWN`; add per-attribute confidence.
5. **Extraction service:** FastAPI container, batch endpoint for bulk jobs, model and rules version reported in output.
6. **Evaluation:** per-attribute accuracy, baseline versus model, results stored into `evaluation_run`; error analysis list for developer4 to extend dictionaries.
7. **Packaging:** Docker image, model weights path configurable, CPU fallback documented. **Needs from others:** labelled sets and synthetic generator (developer4), template list of attributes (developer4). **Done when:** the model matches or beats baseline on critical-attribute accuracy on the frozen test set, or the baseline is presented honestly as the working system.
